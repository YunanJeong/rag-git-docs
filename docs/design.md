# 설계 기록

이 레포를 왜 지금 모양으로 만들었는지 순서대로 적은 기록이다. **사람이 읽는 문서가 아니라, 에이전트가 코드나 문서를 고치기 전에 읽는 설계 맥락이다.**
각 단계가 앞 단계에서 막힌 것을 푸는 순서로 되어 있다. 위에서부터 읽으면 된다.

## 0. 문서의 역할과 작성 규칙

**문서마다 독자가 다르다.** 내용을 어디에 둘지는 독자로 정한다.

| 문서 | 독자 | 담는 것 |
|---|---|---|
| `README.md` | 누구나 | 이 순서로 둔다: 한 줄 요약과 도입부, 빠른 연결(등록 명령과 사용 가이드 링크), 시스템 구조, 수집 방식 비교 표, 서버에 설치하기(운영자용 최소 명령과 운영 가이드 링크), 로컬 PC 에서 직접 설치·운영하기(예외 경로임을 밝히고 운영 가이드로 링크만), 문서 안내 표, 코드 구조. 처음 보는 사람이 붙는 법부터 알게 하고, 개발자용 내용은 뒤로 보낸다 |
| `docs/usage.md` | 쓰는 사람 | 연결하기, 무엇을 물을 수 있나, 어떻게 답하나, 연결 관리, 문제 해결 |
| `docs/operations.md` | 운영자 | 설치·업그레이드, 수집 방식 고르기, 토큰 관리, 네트워크, 로그, 로컬 실행 |
| `docs/design.md` (이 문서) | 에이전트 | 왜 이렇게 만들었는지, 지켜야 할 약속. 사람용 안내는 옮겨 오지 않는다 |
| `docs/proposal-git-clone.md` | 기록 | clone 방식 검토 당시의 기록. 본문은 고치지 않고, 달라진 점은 "검토 때와 달라진 점"에 덧붙인다 |
| `docs/architecture.svg` | 누구나 | README 의 시스템 구조도. 구조가 바뀌면 같이 고친다. 로고는 Simple Icons(CC0)의 path 를 그대로 넣는다 |

README 에는 정상 경로만 짧게 두고, 상세는 usage.md·operations.md 로 링크한다. 같은 내용을 두 곳에 쓰지 않는다.
쓰는 사람이 직접 치는 명령은 usage.md 에 둔다. operations.md 는 그 명령을 다시 적지 않고 usage.md 로 링크한다.

**작성 규칙.**
- 일반론으로 쓴다. 특정 환경의 수치·주소·사례(디스크 크기, 서버 종류, 특정 IP 등)를 문서와 주석에 쓰지 않는다. 그런 값은 `deploy/` 의 values 에만 둔다. 규칙을 적용할 때는 손댄 파일 전체를 직접 찾아 고친다.
- 한 문장 안에서 줄을 바꾸지 않는다. 줄바꿈은 문장 끝에서만 한다.
- README 맨 위에는 무엇을 하는지 한 줄 요약을 둔다.
- 용어: 처음 한 번은 "검색 MCP 서버", 이후 README·운영 문서에서는 "MCP서버" 로 줄여 쓴다. 다른 파일의 "검색 서버" 는 요청이 없으면 그대로 둔다.
- 토큰·비밀값을 말할 때는 어느 것인지 이름으로 밝힌다. 이 레포에는 사용자별 `SERVE_TOKEN`, 수집용 PAT `GITLAB_TOKEN`·`GITHUB_TOKEN`, Qdrant API 키가 있다.
- 동작을 설명할 때는 누가, 무엇을, 어디에 하는지를 밝힌다. 주어와 대상이 빠진 줄임말을 쓰지 않는다.

**values 파일 규칙.**
- `deploy/` 의 api 용과 clone 용 values 는 같은 항목을 모두 적는다. 기본값과 같아도 생략하지 않는다. 주석의 양도 둘이 같게 맞춘다.
- 주석은 짧게, 그 항목이 무엇인지만 적는다.
- 예시 파일(`*.example.yaml`, `local.env.example`)의 비밀값 자리는 비워 두고, 예시는 주석으로 적는다.

**보류한 안건.** MCP서버 인증을 사용자별 토큰 대신 GitLab 계정 로그인(OAuth)으로 바꾸는 안. GitHub 도 지원하는 이 레포에서는 GitHub 쪽 OAuth 가 훨씬 무거워 보류했다.

## 출발점 — 애초에 왜 필요한가

사내 문서를 근거로 LLM 에게 묻고 싶다. 문서가 몇 개뿐이면 **그냥 프롬프트에 파일을
붙여넣으면 된다.** 이 프로젝트는 필요 없다.

문제는 문서가 늘어날 때다. 다 넣으면 컨텍스트에 안 들어가고, 넣을 수 있어도 대부분이
질문과 무관한 내용이라 답이 나빠진다. 그래서 **질문과 관련 있는 부분만 골라내는 앞단**이
필요해진다. 이 프로젝트가 그 앞단이다.

그리고 그 문서들은 한 폴더에 얌전히 있지 않다. 리포 수십 개에 각각 `docs/` 나
`README.md` 로 흩어져 있다. **모으는 것부터가 일이다.**

## 1. 모으기 — `git clone` 을 쓰지 않는 이유

리포를 전부 clone 하면 수집 서버에 **원본 저장소의 사본이 생긴다.** 필요한 건 md 본문뿐인데
`.git` 에는 전체 파일 목록, 커밋 메시지, 작성자 이메일, 과거 이력이 전부 따라온다.
문서 검색 서버가 사고 나면 유출되는 범위가 달라진다.

→ **REST API 로 md 만 받는다.** 리포 목록 → 파일 트리 → blob 내용, 세 번의 호출이다.

채택하지 않은 대안: `--depth 1 --filter=blob:none`, sparse-checkout. 용량은 줄지만
`.git` 이 남는다는 점은 같다.

이 원칙은 기본 방식(`api`)의 것이다. 코드까지 검색하려고 사본을 감수하는 `clone` 방식을
PoC 로 나란히 두었다(19절). 사본을 서버에 둬도 되는지가 확인되기 전까지는 기본값이 아니다.

파일을 받을 때 **경로가 아니라 blob SHA 로 요청한다.** `files/:path/raw` 는 경로를
URL 인코딩해야 하는데, 한글·공백·`#` 이 든 경로에서 인코딩이 한 번 어긋나면 404 다.
SHA 는 16진수라 그 문제가 없다.

## 2. 매번 전부 받으면 안 되나 — manifest 와 blob SHA

리포 수십 개를 매번 전부 내려받으면 API 에 부담이고 느리다.
그런데 API 로 받으면 `git pull` 이 공짜로 해주던 "뭐가 바뀌었나"를 알 수 없다.

→ 파일 트리에 **blob SHA 가 같이 온다.** 경로 → SHA 를 `.manifest.json` 에 적어두고,
SHA 가 같으면 내려받기를 건너뛴다.

SHA 는 **내용의 해시**다. 그래서 브랜치를 `master` → `main` 으로 바꿔도, 파일을
옮겼다가 되돌려도, 내용이 같으면 재다운로드가 일어나지 않는다. 수정 시각 기반이었다면
이 중 어느 것도 성립하지 않는다.

## 3. GitLab 과 GitHub 은 얼마나 다른가

같은 코드로 둘 다 된다고 말하기는 쉽다. 실제로 짜 보면 **공용인 부분과 아닌 부분이
분명하게 갈린다.**

| | 공용 | 벤더별 |
|---|---|---|
| HTTP GET, `Link` 헤더 페이지네이션 | ✓ | |
| md 선별 (`type=="blob"`, mode ≠ 심링크·서브모듈, `.md`) | ✓ | |
| manifest 대조, 삭제 판정, 파일 쓰기 | ✓ | |
| 청킹, 임베딩, 저장 | ✓ | |
| 인증 헤더 이름 | | `PRIVATE-TOKEN` vs `Authorization: Bearer` |
| 엔드포인트 URL 세 개 | | 모양이 다르다 |
| 리포 경로 필드 | | `path_with_namespace` vs `full_name` |
| 트리 SHA 필드 | | `id` vs `sha` |

**md 선별이 공용인 게 핵심이다.** `type: "blob"` 과 mode 값 `100644`·`120000`·`160000` 은
git 객체 모델을 그대로 내보낸 것이라 두 벤더가 글자까지 같다. 껍데기만 다르지 같은 git 이다.

그래서 호출 흐름(리포 목록 → 트리 → blob)은 동일하고, **벤더 파일은 각 40줄쯤**이다.
ABC 도 Protocol 도 팩토리도 두지 않았다 — 구현체가 둘뿐이라 dict 조회 한 줄이면 된다.

**진짜로 동작이 다른 건 하나다.** GitHub 의 트리 API 는 페이지네이션이 없다.
`?recursive=1` 로 전부 주거나, 너무 크면 `"truncated": true` 를 붙여 **앞부분만 준다.**
이걸 안 보면 "파일이 사라졌다"로 읽혀 5절의 삭제 로직이 멀쩡한 문서를 지운다.
그래서 `github.py` 는 `truncated` 를 보고 예외를 던지고, 그 리포는 삭제 대상에서 빠진다.

## 4. 경로를 평평하게 펴면 안 되나

`repo-a/docs/deploy.md` 와 `repo-b/docs/deploy.md` 를 한 폴더에 넣으면 이름이 부딪힌다.
해시를 붙여 `deploy-a3f1.md` 로 만들면 충돌은 없어진다.

→ **원본의 디렉터리 구조를 그대로 유지한다.** `DOCS_DIR/<리포 경로>/docs/deploy.md`.

이유는 6절에 있다. 청킹이 파일 경로를 조각의 맥락(브레드크럼)으로 쓰기 때문에,
경로를 뭉개면 검색 품질이 같이 뭉개진다. 저장 구조가 검색 품질에 직접 연결된다.

## 5. 삭제가 제일 무섭다

문서가 지워지면 로컬에서도 지워야 한다. 안 그러면 없어진 문서가 검색에 계속 나온다.
그런데 삭제 로직은 잘못 돌면 **문서를 날린다.** 세 겹으로 막았다.

**첫째, 조회에 성공한 리포만 삭제 대상이다.** 트리 API 가 500 이나 403 을 던졌을 때
"파일이 하나도 없다"로 읽으면 그 리포 문서가 통째로 지워진다. 일시적인 네트워크 장애로
문서가 날아가는 셈이다. 실패한 리포는 삭제 계산에서 아예 빠진다.

**둘째, manifest 에 기록된 파일만 지운다.** `rmtree` 로 디렉터리를 통째로 날리지 않는다.
`DOCS_DIR` 을 잘못 잡아 홈 디렉터리를 가리켰을 때, 수집기가 적어둔 적 없는 파일은
건드릴 수 없다는 보장이 여기서 나온다.

**셋째, 리포 목록이 0개로 오면 멈춘다.** GitLab 토큰 권한이 빠지면 API 가 오류 없이 빈 목록을
주는 경우가 있다. 그대로 진행하면 모든 리포가 "사라졌다"로 판정돼 전부 지워진다.

**도중에 실패하면 기록을 저장하지 않는다.** manifest 는 마지막에 한 번만 쓴다. 중간에
예외로 끝나면 이번 실행의 판정이 기록에 남지 않아, 다음 실행이 같은 일을 처음부터 다시 한다.

## 6. 청킹(쪼개기) — 그런데 맥락이 날아간다

관련된 부분만 넘기려면 처음부터 조각 단위로 저장해야 한다. 문서를 이렇게 조각내는 걸
**청킹(chunking)** 이라고 한다. 여기서는 헤더를 기준으로 자른다.

그랬더니 새 문제가 생겼다. 조각만 떼어 놓으니 무슨 얘긴지 모르겠다. `재발급하면 통계가
끊긴다` 라는 조각은 어느 리전 문서인지, 무엇을 재발급한다는 건지 알 수 없다.

→ 조각 앞에 `[파일 > 헤딩]` 한 줄을 붙여 같이 저장한다. 맥락도 검색 대상에 포함된다.
4절에서 경로 구조를 유지한 이유가 이것이다.

같은 이유로 **수집할 때 BOM 을 떼어낸다.** BOM 이 남으면 첫 줄이 `﻿# 제목` 이 되어
헤딩 정규식에 안 걸리고, 문서 전체가 헤딩 없는 한 덩어리가 되면서 브레드크럼을 잃는다.
수집기의 한 줄이 검색 품질을 좌우하는 지점이다. `clone` 방식은 작업 트리를 고칠 수 없어
수집 때 떼지 못하므로, `index.py` 가 읽을 때도 한 번 더 뗀다.

## 7. 임베딩(숫자로 바꾸기) — 문자열 비교로는 관련 문서를 못 찾는다

`쿠버네티스 워커 늘리기` 와 `노드그룹 desired 조정` 은 **겹치는 글자가 하나도 없는데
같은 얘기일 수 있다.** Elasticsearch 처럼 글자로 색인하는 저장소는 유의어 사전을 사람이
직접 채우지 않는 한 못 찾는다.

→ 조각을 **숫자 목록(vector)** 으로 바꿔서 저장한다. 이 변환이 **임베딩(embedding)**,
변환해주는 AI 모델이 **임베딩 모델**이다.

```
"노드그룹 desired 조정"   →  [0.21, -0.04, 0.88, ... ]   ← 숫자 1024개
"쿠버네티스 워커 늘리기"  →  [0.19, -0.07, 0.85, ... ]   ← 값이 비슷하다
"배포 스크립트 롤백"      →  [-0.63, 0.41, 0.02, ... ]   ← 값이 다르다
```

뜻이 비슷하면 숫자도 가까워지도록 학습된 모델이다. 그래서 "의미가 비슷한가"를 **숫자 사이의 거리 계산**으로 바꿀 수 있고, 그 계산을 대신해주는 저장소가 **벡터 DB** 다.

단, **DB 는 의미를 모른다.** 의미를 아는 건 임베딩 모델뿐이다. 그래서 넣을 때 한 번 돌리고
끝이 아니라 **검색할 때마다 질문도 같은 모델로 벡터로 바꿔** 넘겨야 하고, DB 는 받은 벡터로
가까운 것만 찾아준다. 색인과 다른 모델을 쓰면 값이 안 맞아 결과가 무의미해진다 —
`EMBED_MODEL` 이 색인·검색 공통 설정인 이유다.

> 임베딩 모델은 **LLM(언어생성모델) 이 아니다.** 글을 쓰는 게 아니라 벡터로 바꾸는 것만 학습한 별개 모델군이다. Claude Code 를 이 DB 에 붙이면 답은 Anthropic 모델(Claude Opus 등)이, 벡터는 bge-m3 가 만든다. Anthropic 은 임베딩 API 가 없어 그 자리는 항상 별도 모델이다.

## 8. 어떤 임베딩 모델을 쓰나 — 문서를 밖으로 내보낼 순 없다

OpenAI 임베딩 API 같은 걸 쓰면 색인할 때마다 사내 문서 전문이 외부로 나간다.
1절에서 clone 을 피한 이유와 같은 종류의 문제다.

→ **bge-m3** 를 로컬에서 돌린다. 문서가 나가지 않고 외부 임베딩 API 키도 필요 없다. 다국어 모델이라 한국어가 되고, 8번에 필요한 두 종류 벡터를 한 번에 내준다.

## 9. 의미로만 찾으면 고유명사를 구별 못 한다

사내 리전 코드처럼 **한 글자만 다른 식별자**로 검색하면 엉뚱한 문서가 같이 딸려 나온다.
임베딩 모델이 학습한 적 없는 사내 고유명사라서, 둘이 거의 같은 숫자가 되기 때문이다.

→ 성격이 반대인 **두 종류의 벡터**를 같이 쓴다. bge-m3 가 둘 다 내준다.

- **dense**(밀집) — 지금까지 말한 그 1024개 숫자. 문장 전체의 뜻을 담는다.
- **sparse**(희소) — 단어 하나가 칸 하나인 아주 긴 목록. 그 조각에 나온 단어의 칸에만
  중요도 점수가 들어가고 나머지는 전부 0 이라 "희소"다. 같은 단어가 글자 그대로
  나와야 점수가 붙는다.

```
sparse:  ... region-a: 0.8 ... serverid: 0.6 ... (나머지 수만 칸은 0)
```

| | 잘하는 것 | 못하는 것 |
|---|---|---|
| **dense** | 표현이 달라도 뜻이 같으면 찾음 | 한 글자 다른 식별자 구별 |
| **sparse** | 글자가 정확히 맞는 것을 찾음 | 표현이 다르면 못 찾음 |

두 검색을 각각 돌리고 순위를 합친다(RRF). 한쪽의 약점을 다른 쪽이 메운다.

## 10. 어떤 벡터 DB 를 쓰나 — Chroma vs Qdrant

| | Chroma | Qdrant |
|---|---|---|
| 형태 | 파이썬 라이브러리. 임포트하면 끝 | 서버. 컨테이너로 띄운다 |
| 쓰는 자리 | 노트북, 프로토타입 | 여러 클라이언트가 붙는 공용 검색 |

Chroma 가 훨씬 간편하지만 쓰지 않았다. **Chroma 로 충분한 규모면 출발점으로 돌아가
프롬프트에 파일을 붙여넣는 게 낫기 때문이다.** 벡터 DB 가 값을 하는 건 문서가 많아
다 못 넣거나 여러 사람이 색인을 공유할 때고, 그 지점을 목표로 하면 처음부터 서버형이
맞다.

## 11. 색인도 증분으로 — 바뀐 조각만 임베딩한다

처음에는 `index.py` 가 매번 새 컬렉션을 처음부터 채웠다(전량 재색인). 문서가 1000개 남짓일 때는 몇 분이면 끝났고, 삭제된 문서의 조각이 DB 에 남는 문제도 저절로 생기지 않았다.
문서가 수천 개로 늘자 CPU 로 하루 수십 분씩 걸렸다. 그날 실제로 바뀐 문서는 수십 개뿐인데, 나머지 전부를 어제와 똑같이 다시 계산하고 있었다. 그래서 바꿨다.

**임베딩은 조각마다 독립이다.** 조각 하나의 벡터는 그 조각의 글자와 모델만으로 정해진다. 따로 넣든 함께 넣든 같은 벡터가 나오므로, 바뀐 조각만 다시 계산해도 결과가 전량과 같다.

**조각 ID 를 내용으로 만든다.** ID 는 `uuid5(설정 버전 + 파일 경로 + 조각 내용)` 이다(`store.point_id`). 조각 내용에는 첫 줄의 `[경로 > 헤딩 | 수정 날짜]` 가 들어가므로, md 를 고치면 그 md 의 조각 ID 가 모두 바뀌고 다른 md 의 ID 는 그대로다.

**매번 통째로 비교한다.** 지금 md 로 계산한 ID 집합과 Qdrant 에 들어 있는 ID 집합(벡터와 본문 없이 ID 만 받는다)을 비교해, 새 ID 의 조각만 임베딩해 넣고 사라진 ID 를 지운다.
수집이 아는 "바뀐 파일 목록" 은 넘겨받지 않는다. 그 목록에 기대면 한 번 틀렸을 때 DB 가 계속 어긋난 채로 남는다. 통째로 비교하면 지난 실행이 어떻게 끝났든 이번 실행이 끝나면 md 와 DB 가 같아진다.
비교 비용은 ID 목록을 받고 집합을 빼는 것뿐이라, 조각이 수만 개여도 몇 초다. 비싼 것은 임베딩이고, 그 양이 바뀐 만큼으로 줄어든다.

- **넣기를 먼저, 지우기를 나중에 한다.** 반대로 하면 고친 문서의 옛 조각을 지운 뒤 새 조각을 넣기 전까지 그 문서가 검색에서 사라진다. 이 순서면 잠깐 옛 것과 새 것이 함께 보일 뿐 사라지는 순간이 없다.
- **임베딩해 넣는 일은 일정 개수씩 끊어서 한다(`BATCH`).** 전부를 메모리에 쥐지 않으므로 조각이 아무리 많아도 메모리가 일정하다.
- **모델이나 자르기 설정이 바뀌면 `store.VERSION` 을 바꾼다.** ID 에 들어가므로 모든 조각의 ID 가 달라져, 같은 비교가 전부를 다시 넣고 옛 것을 지운다. 첫 색인도 같은 경로다. 빈 DB 에서는 모든 조각이 새 조각이다.
- **새로 임베딩할 조각이 없으면 모델을 올리지 않는다.**
- 조각의 payload 에는 본문(`text`)과 함께 파일 경로(`path`)를 둔다. 매일의 비교에는 쓰지 않지만, 파일 하나의 조각만 찾거나 지울 때 쓴다.

## 12. 색인하는 동안 검색은 어떻게 되나

처음에는 컬렉션을 지우고 다시 채웠다. 주기 실행에 걸고 검색 서버를 상주시키자 지운 순간부터 다 채울 때까지 검색이 비었다.
그래서 **별칭(alias)** 을 두었다. 검색은 `docs` 라는 이름으로 하는데, 그건 실제 컬렉션이 아니라 `docs_<시각>` 컬렉션을 가리키는 별칭이다. 전량 재색인 시절에는 새 컬렉션을 다 채운 뒤 별칭만 옮겼다.

증분으로 바꾼 뒤에는 컬렉션을 새로 만들지 않고, 별칭이 가리키는 컬렉션 하나를 계속 고쳐 쓴다. 첫 색인 때만 `<별칭>_<시각>` 컬렉션을 만들어 별칭을 건다.
검색이 비는 순간은 11절의 "넣고 나서 지운다" 순서가 막는다.

**실패하면 다음 실행이 고친다.** 색인이 중간에 죽으면 DB 가 반쯤 맞춰진 채 남는다. 다음 실행이 통째로 비교하므로 저절로 맞춰진다.
다만 수집이 "바뀐 것 없음"(종료 코드 3)이면 색인을 건너뛰는데, 그날 건너뛰면 반쯤 맞춰진 상태가 이어진다. 그래서 색인이 끝까지 성공했을 때만 `DOCS_DIR/.indexed` 에 설정 버전을 적어 두고, 이 표시가 있고 버전이 같을 때만 건너뛴다. 색인을 시작하면 표시부터 지운다.

별칭 이름은 `QDRANT_ALIAS` 로 바꿀 수 있고 기본값은 `docs` 다. Qdrant 하나를 여러 릴리스가 같이 쓸 때 릴리스마다 다르게 준다.

## 13. 검색을 에이전트에 어떻게 붙이나 — 부를 때마다 모델을 올리면 못 쓴다

찾은 조각을 LLM 에게 넘기는 방법이 있어야 RAG 가 완성된다. 가장 쉬운 건 검색 스크립트를
만들어 Claude Code 에게 셸로 실행하라고 하는 것이다. 돌아는 간다.

문제는 **실행할 때마다 bge-m3 를 새로 올린다는 것**이다. 한 번에 수 초가 걸리고,
에이전트는 한 질문에도 검색을 여러 번 한다. 쓸 수 있는 속도가 아니다.

→ **모델을 올려 둔 채 상주하는 서버를 둔다.** `serve.py` 가 기동 때 모델을 한 번 올리고,
이후 질의는 임베딩 한 번과 Qdrant 조회 한 번으로 끝난다. GPU 에서 첫 질의는 약 0.9초,
이후는 30~50ms 다. CPU 만 있어도 질의 한 건이 80~100ms 라 체감 차이가 없다.

서버와 에이전트 사이는 **MCP(Model Context Protocol)** 로 붙는다. 에이전트가 도구 목록을
받아 보고, 필요할 때 스스로 부르는 표준 규약이다. 도구는 `search_docs` 하나다.

전송은 stdio 가 아니라 HTTP 다. stdio 로 띄우면 에이전트 세션마다 서버 프로세스가 새로
떠서, 모델도 세션마다 다시 올라간다. 상주시키는 의미가 없어진다.

LLM 을 부르는 코드는 따로 두지 않았다. 답을 쓰는 건 이미 붙어 있는 에이전트다.
슬랙봇처럼 에이전트 없이 사람이 바로 묻는 곳이 생기면 그때 LLM 호출이 필요해진다.


## 14. 검색 서버 인증 — 사용자별 토큰

검색 서버는 네트워크로 열린다. 그래서 인증이 있어야 한다.
작은 팀이면 OAuth 까지 갈 필요 없이 `Authorization: Bearer` 로 토큰을 확인하는 ASGI 래퍼 하나면 된다(`auth.py`).
검색 서버 토큰(`SERVE_TOKEN`)이 비어 있으면 서버가 아예 뜨지 않게 해서, 실수로 토큰 없이 열리는 일을 막는다.

**토큰은 사람마다 따로 준다.** `SERVE_TOKEN` 에 `이름:토큰` 을 쉼표로 이어 넣는다.
토큰 하나를 같이 쓰면 한 사람만 끊을 수 없고, 누가 무엇을 봤는지도 가릴 수 없다. clone 모드에서는 토큰 하나로 전 리포의 코드를 읽을 수 있어 이 둘이 더 무겁다.
사람을 더하거나 빼는 일은 `SERVE_TOKEN` 에서 한 항목을 고치고 upgrade 하는 것으로 끝난다. Secret 이 바뀌면 검색 서버 파드가 다시 뜬다.
형식이 틀렸거나 이름·토큰이 겹치면 뜨지 않는다. 오류 문구에는 이름만 넣고 토큰은 넣지 않는다.

**도구를 부를 때마다 누가 불렀는지 남긴다.** `<시각> <이름> <도구> <인자>` 한 줄을 검색 서버 로그(표준 출력)에 쓴다.
HTTP 요청마다 남기지 않는 것은, MCP 는 도구 한 번 부르는 데 요청이 여러 번 오가서 정작 무엇을 했는지가 묻히기 때문이다.
도구 함수를 감싸 SDK 가 넣어 주는 요청 정보(`Context`)에서 헤더를 읽는다. 감싸도 도구 이름·설명·인자 스키마는 원래 함수 그대로다.
파드가 다시 뜨면 로그도 사라지므로, 오래 둘 기록이 필요하면 로그 수집을 따로 붙인다.

MCP SDK 는 `127.0.0.1` 로 들어온 요청만 통과시키는 Host 헤더 검사(DNS rebinding 방어)를
켜 둔다. Service 를 거쳐 노드 IP 로 들어오는 요청이 이 검사에 막히므로 끄고, 검색 서버 토큰으로 막는다.

**서버에서는 인증을 빼지 않는다.** 인증 없이 `127.0.0.1` 에만 띄우면 SSH 터널, `kubectl port-forward` 같은 우회를 덧붙이게 된다.
쿠버네티스에서 서비스를 밖에 여는 정석은 Service 이고, 그러려면 인증이 있어야 한다.

**`AUTH_MODE=none` 은 자기 PC 에서 혼자 쓰는 로컬 실행용이다.** 기본값은 `token` 이다. `none` 은 인증이 없으므로 `SERVE_HOST` 가 `127.0.0.1`·`localhost`·`::1` 이 아니면 뜨지 않는다.
막는 것은 이 한 가지뿐이다. 서버는 Service 로 접속을 받으려면 `0.0.0.0` 으로 떠야 하므로, 이 값이 서버에 잘못 들어가도 검사에 걸려 인증 없이 열리지 않는다. 호출 로그의 이름은 `local` 이다.

**동시 요청은 락으로 막는다.** 10명이 동시에 검색하는 부하를 걸었을 때 프로세스가
세그폴트로 죽었다. FlagEmbedding 은 `encode` 때마다 `model.to(device)` 로 가중치를 다시
옮기는데, MCP SDK 가 동기 도구 함수를 요청마다 스레드에서 돌려서 두 스레드가 같은
가중치를 동시에 옮기다 터진다. 사람 수가 아니라 요청이 겹치느냐의 문제라, 에이전트가
검색을 병렬로 부르면 한 사람만 써도 생길 수 있다. `encode` 를 `threading.Lock` 으로 감싸
한 번에 하나만 돌린다. GPU 한 장에서는 병렬로 돌려도 빨라지지 않아 잃는 것이 없다.
같은 부하에서 50건 모두 성공했다.

## 15. 폴더를 단계별로 나눈 이유

처음엔 전부 한 폴더에 넣고 `gitlab.py`, `sync.py` 를 청킹·임베딩 옆에 두었다. 돌아는 갔다.
문제는 **레포 이름이 `rag-git-docs` 인데 `gitlab` 이 여기저기 박혀 있었다는 것**이다.
GitHub 을 붙이려면 여러 파일을 동시에 고쳐야 하는 상태였다.

그래서 실행 단계마다 폴더를 하나씩 두었다. 1 단계 수집은 `collector/`, 2 단계 색인은
`indexer/` 다. GitLab 과 GitHub 의 API 차이는 수집 안에서만 의미가 있으므로
`collector/sources/` 아래에 호스팅마다 파일 하나로 둔다.

| 폴더 | 아는 것 | 모르는 것 |
|---|---|---|
| `collector/sources/` | API 주소, 인증 헤더, 응답 필드 이름 | 받은 파일을 어디에 쓰는지 |
| `collector/` 의 나머지 | 파일 경로와 blob SHA | 그게 GitLab 에서 왔는지 GitHub 에서 왔는지 |
| `indexer/` | md 파일과 Qdrant | 그 파일이 어떻게 모였는지 |

`collector/` 와 `indexer/` 는 **서로를 import 하지 않는다.** 둘은 `DOCS_DIR` 의 파일로만
이어지고, 조립은 루트의 실행 파일에서만 일어난다.

`collector/manifest.py` — 문서가 날아가는 가장 위험한 코드 — 는 **가져다 쓰는 모듈이
하나도 없다.** `dict[str, str]` 두 개를 받아 리스트를 돌려줄 뿐이라 네트워크도 디스크도
없이 테스트로 묶인다. 객체 대신 `dict` 를 받게 시그니처를 좁힌 덕이다.

## 16. 모듈 이름 — rag, retrieval, vectordb, indexer

PoC 에서 가져온 모듈은 처음에 `rag/` 였다. RAG 는 검색, 프롬프트 보강, 답 생성 세
단계를 합친 말이라 이 모듈보다 훨씬 넓다.

`retrieval/` 로 바꿨는데 이것도 틀렸다. "RAG 의 앞부분이니 retrieval" 로 넘겨짚었을 뿐,
안을 보면 대부분이 **원본 문서를 잘라 벡터 DB 에 넣는 코드**다.

그래서 `indexer/` 로 정하고, 이름대로 색인만 하게 했다. 검색 코드는 `serve.py` 로 옮겼다.

`serve.py` 는 그래도 `indexer/` 의 두 파일을 가져다 쓴다.
- `embed.py` — 질문을 문서 조각과 비교하려면 질문도 색인 때와 같은 임베딩 모델로 벡터로
  바꿔야 한다. 모델이 다르면 같은 뜻이어도 전혀 다른 숫자가 나와 비교가 안 된다.
- `store.py` 의 `client()` 와 `ALIAS` — 색인이 쓴 것과 같은 Qdrant 와 같은 별칭을 읽어야 한다.

## 17. 최소 분량으로 줄이며 뺀 것

서버 1대로 팀이 쓰는 규모에서 없어도 되는 것은 뺐다. 필요해지면 다시 넣는다.

| 뺀 것 | 이유 |
|---|---|
| HTTP 재시도, 같은 페이지 반복 방지 | 실패하면 다음 실행이 같은 일을 다시 한다 |
| 경로 검사(`..`, 절대경로), 임시 파일 후 바꿔치기 | 받는 쪽이 설정한 GitLab 그룹뿐이다 |
| 리포별 내려받기 실패 집계 | 실패하면 기록을 저장하지 않고 끝나서 다음 실행이 다시 받는다 |
| 검색 스크립트, 수집 후 색인을 묶은 스크립트 | 수집과 색인은 CronJob 하나에서 차례로 돈다 (18절) |
| 청커의 긴 섹션 분할 | 헤딩 단위로만 자른다. 임베딩 길이를 2048 토큰으로 늘려 잘리지 않는다 |

**줄여도 빼면 안 되는 것.** 증분 수집, 조회 실패한 리포 보호, 색인의 "넣고 나서 지우는" 순서와 완료 표시(`.indexed`)는 분량을 줄일 때 같이 빼기 쉽다.
이것들은 분량이 아니라 **문서가 날아가거나 검색이 비는 것**을 막는 장치라 빼면 안 된다.
`index.py` 의 "md 가 하나도 없으면 멈춘다" 도 같다. 통째로 비교하므로, 빈 목록으로 돌면 들어 있는 조각이 전부 지워진다.

## 18. 어디서 돌리나 — 컨테이너로 k3s 에

Qdrant 가 k3s 에 있으니 파이썬도 같은 클러스터에 넣었다. 처음에는 호스트에서 uv 로 돌리고
systemd 로 상주와 매일 실행을 맡겼는데, 그러면 Qdrant 는 k3s 가, 나머지는 systemd 가
관리하는 두 갈래가 된다.

Qdrant 의 NodePort(30633)는 남겨 둔다. 앱은 클러스터 안에서 Service 이름으로 붙으므로
쓰지 않지만, 로컬에서 `index.py` 를 직접 돌려 볼 때 쓴다.

**k8s 에 올리는 것은 전부 Helm 차트로 한다.** Qdrant 는 공식 차트에 values 만 넘기고,
앱은 `charts/rag-git-docs/` 차트로 띄운다. `kubectl create` 같은 명령으로 만든 리소스는
무엇을 만들었는지 파일에 남지 않고, 날 매니페스트를 apply 하면 지울 때 무엇이 함께
만들어졌는지 추적하기 어렵다. 차트면 `helm uninstall` 한 번으로 정리된다.

**차트 소스와 배포는 나눈다.** `charts/rag-git-docs/values.yaml` 은 차트의 기본값이자
규격이다. 어디에 설치해도 맞는 일반적인 값만 두고, 이 환경의 값(이미지 주소, NodePort,
스토리지 클래스, Qdrant 주소)은 넣지 않는다. 이 환경의 값은 `deploy/rag-git-docs.values.yaml`
에 두고 설치할 때 `-f` 로 덮는다. Qdrant 도 같은 방식이라, 배포 쪽에서는 두 차트 모두
"패키지(`deploy/packages/*.tgz`) + 덮어쓸 values" 로 똑같이 다룬다.

Secret 도 따로 만들지 않는다.
- Qdrant API 키는 Qdrant 차트가 `apiKey: true` 로 만들어 `rag-qdrant-apikey` 에 둔다.
  이미 있으면 그 값을 다시 쓰므로 `helm upgrade` 를 해도 Qdrant API 키가 바뀌지 않는다.
  앱 차트는 같은 Secret 에서 Qdrant API 키를 읽는다.
- GitLab 토큰은 앱 차트가 `secretEnv` 값으로 Secret 을 만든다. 토큰은
  `deploy/rag-git-docs.secret.yaml` 에 적어 `-f` 로 넘기고, 그 파일은 `.gitignore` 에 넣는다.

이미지 하나로 세 진입점을 다 돌린다. 무엇을 돌릴지는 템플릿의 `command` 가 정한다.

| 리소스 | 하는 일 |
|---|---|
| Deployment | `serve.py` 상주. 죽으면 k8s 가 다시 띄운다 |
| CronJob | 매일 03:00 에 `collect.py` 다음 `index.py` |
| PVC 둘 | 수집한 md 와 manifest, bge-m3 모델 캐시 |

**PVC 를 빠뜨리면 조용히 망가진다.** CronJob 은 매번 새 파드로 뜬다. 문서 디렉터리가
볼륨이 아니면 `.manifest.json` 이 매번 사라져, 오류 없이 매일 전부 새로 받는다. 모델
캐시가 볼륨이 아니면 실행마다 2.3GB 를 새로 받는다.

**수집이 실패해도 색인은 돌린다.** `collect.py` 는 리포 하나만 실패해도 종료 코드 1 로
끝난다. 그때 색인을 멈추면 그 리포가 고쳐질 때까지 매일 색인이 안 돈다. 실패한 리포의
옛 파일은 지우지 않으므로 그대로 색인해도 된다. 그래서 `&&` 대신 `;` 로 잇는다.

`concurrencyPolicy: Forbid` 로 색인이 길어져도 다음 실행과 겹치지 않게 한다. 겹치면
두 파드가 같은 문서 디렉터리를 동시에 건드린다.

**검색 서버는 NodePort Service 로 연다.** 노드의 `30876` 포트로 들어온 요청이 파드의
8765 로 간다. 누가 붙을 수 있는지는 방화벽(클라우드라면 보안그룹)에서 이 포트를 열 IP 로 정하고,
붙은 요청은 14절의 검색 서버 토큰으로 한 번 더 거른다.

LoadBalancer 대신 NodePort 인 이유는 노드가 하나라서다. k3s 의 기본 LoadBalancer 구현은
노드 IP 에 포트를 여는 것이라, 노드가 하나면 NodePort 와 하는 일이 같다.

검색 서버 토큰과 검색 내용은 평문 HTTP 로 오간다. 접근을 쓰는 사람의 IP 로만 좁히면 괜찮지만,
넓게 열 거면 앞에 TLS 를 두어야 한다.

**이미지는 레지스트리에서 받는다.** 처음에는 노드에서 빌드한 이미지를 `k3s ctr images import`
로 직접 넣었다. 레지스트리가 없어도 되지만 차트 밖의 수동 단계이고, 노드를 새로 만들면
이미지가 사라진다. 차트는 `image.repository` 와 `image.tag` 만 가리킨다. 비공개 이미지면
레지스트리 로그인 Secret 이름을 `image.pullSecret` 에 적는다.

## 19. 코드까지 보려면 — clone 방식을 갈아엎지 않고 나란히 둔다

문서만으로는 "그 설정 키가 실제로 어디서 읽히나" 같은 질문에 답하지 못한다. 코드를 보려면
리포가 통째로 있어야 하고, 그러면 1절에서 피한 **서버의 코드 사본**이 생긴다.

그래서 두 방식은 **보안과 품질 사이의 선택**이다. 기술적 차이는 그 결과일 뿐이다.
- `api`(md only)는 보안을 우선한다. 서버에 md 본문만 남아, 서버나 백업이 새도 유출 범위가 문서에서 그친다.
  코드에 커밋된 시크릿도 들어오지 않는다. 검색 서버 토큰이 새도 문서 조각 검색밖에 못 한다.
- `clone`(리포 전체)은 답의 품질과 관리 편의를 얻는다. 코드를 근거로 답할 수 있고, 증분·삭제·날짜를 git 이 대신한다.
  대신 코드와 이력의 사본, 이력째 들어오는 시크릿, 토큰 하나로 전 리포 코드를 읽을 수 있는 서버를 감수한다.

사본을 둬도 되는지 아직 확인되지 않아서, 기존 방식을 지우지 않고 **PoC 로 나란히 둔다.** 기본값은 `api` 다.
검토 과정은 `docs/proposal-git-clone.md`, 고르는 기준은 README 에 있다.

**고르는 것은 환경변수 하나다.** `COLLECT_MODE=api|clone`. 파이썬으로 직접 돌리든, 도커든, 헬름이든 같다.
`collect.py` 는 이 값을 보고 `collect_api.py` 나 `collect_clone.py` 를 부르기만 한다.
두 진입점 모두 조립만 하고, 일은 각자의 폴더가 한다. `serve.py` 도 같은 값을 보고 코드 도구를 노출할지 정한다.

| | 아는 것 | 모르는 것 |
|---|---|---|
| `collector/` | API 로 md 받기, blob SHA manifest | clone 이 있는지 |
| `cloner/` | git clone·fetch, 커밋 해시 기록, 코드 읽기 | md 를 어떻게 자르는지 |
| `indexer/`, `index.py` | md 파일과 Qdrant | 어느 방식으로 모였는지 |
| 헬름 차트 | 볼륨과 환경변수를 어느 파드에 넣는지 | 수집 방식이 무엇인지 |

`cloner/` 가 `collector/` 에서 가져다 쓰는 건 `collector/sources/` 의 리포 목록과 git 인증 정보뿐이다.
어느 호스팅이냐를 아는 곳은 여전히 거기 하나다. clone 은 SHA 비교·파일 쓰기가 필요 없어
`collector/` 의 나머지와는 다른 길이라, `sources/` 에 끼우지 않고 진입점을 따로 두었다.

**헬름 차트는 수집 방식을 모른다.** 처음에는 `collectMode` 값을 두고 차트가 볼륨과 환경변수를 갈랐다.
그러면 방식이 하나 늘 때마다 차트 템플릿도 고쳐야 한다. 지금은 values 의 `env` 를 CronJob 과 검색 서버
양쪽에 환경변수로 그대로 넣기만 한다. 볼륨도 방식과 상관없이 같다. 수집이 쓰는 `-docs` 볼륨 하나를
CronJob 은 읽고 쓰기로, 검색 서버는 읽기 전용으로 `/data` 에 붙인다. api 방식에서는 검색 서버가
이 볼륨을 읽지 않는다. 이미 Qdrant 에 색인된 md 사본이라 붙여 둬도 노출되는 것이 늘지 않는다.

**색인과의 약속은 세 가지이고, 두 방식이 똑같이 지킨다.** 그래서 `index.py` 는 방식을 모른다.
- `DOCS_DIR` 아래 md 가 `<그룹>/<리포>/<리포 안 경로>` 에 있다. clone 디렉터리가 곧 이 구조다.
- 바뀐 게 없으면 수집이 종료 코드 3 을 낸다. clone 은 모든 리포의 커밋 해시가 지난번과 같으면 3 이다.
- `.manifest.json` 의 `dates` 에 `"리포/파일" → 마지막 커밋일` 이 있다. clone 은 커밋이 바뀐 리포만
  `git log --name-only` 를 한 번 훑어 구한다. 파일마다 API 를 부르던 것보다 싸다.

`index.py` 가 md 를 찾을 때 `.git` 디렉터리, 심링크, `._` 로 시작하는 파일을 거른다. clone 에는
이것들이 섞이고, 심링크는 리포 밖을 가리킬 수 있다.

**두 방식은 같은 디렉터리를 쓰지 않는다.** api 는 `리포/docs/a.md` 를 파일로 쓰고, clone 은 `리포/` 를
git 작업 트리로 쓴다. 같은 곳에서 돌면 서로의 파일을 덮어쓴다. 그래서 같은 볼륨 안에서 `DOCS_DIR` 을
나눈다(api 는 `/data/docs`, clone 은 `/data/repos`). `COLLECT_MODE` 만 바꾸고 `DOCS_DIR` 을 빠뜨리는 실수를
막으려고, clone 의 `.manifest.json` 에 `mode: clone` 을 적는다. 상대 방식의 기록이 있는 디렉터리면 두 수집기
모두 종료 코드 2 로 시작하지 않는다. 방식을 바꿔도 각자의 디렉터리가 남아 있으므로, 되돌리면 이어서 쓴다.

**PoC 는 api 와 동시에 띄워 비교한다.** 네임스페이스와 릴리스를 따로 두면 볼륨·Service·Secret 이 저절로 나뉘고, Qdrant 도 네임스페이스마다 하나씩 둔다.
그래서 Qdrant 별칭 `docs` 도 부딪히지 않는다. 한 노드에서 겹치는 것은 클러스터 전체에서 하나뿐인 노드 포트와, CPU 를 다투는 CronJob 시각뿐이다.
`deploy/*.clone.values.yaml` 은 api 용과 같은 항목을 모두 적은 별도 파일이고, 그 파일 하나로 설치한다. 기본값이라도 생략하지 않아, 파일만 보고 그 릴리스의 설정을 알 수 있게 했다.

한 릴리스 안에서 갈아끼우는 경우의 볼륨 크기는 차트가 따로 정하지 않는다. clone 을 쓸 릴리스는 `persistence.docs.size` 를 리포 전체 크기에 맞춰 잡는다.
local-path 처럼 크기를 강제하지 않는 스토리지라면 실제 한도는 노드 디스크다. 확장을 지원하지 않는 스토리지라면 이미 만든 PVC 의 크기는 바꿀 수 없다.

**5절의 원칙을 clone 에도 그대로 적용한다.**
- 받기에 실패한 리포는 옛 clone 을 두고, 삭제 대상에서도 뺀다.
- 기록(`heads`)에 있는 clone 만 지운다.
- 리포 목록이 0개면 멈춘다.
- 도중에 실패하면 기록을 저장하지 않는다.

처음 받는 clone 은 `<리포>.clone-tmp` 에 받고, 다 받은 뒤에 이름을 바꾼다. 리포 전체를 받다가 파드가
죽어도, 반쯤 받은 clone 이 정상 clone 처럼 남지 않는다.

**pull 대신 fetch 후 reset 한다.** 기본 브랜치가 바뀌거나 강제 push 가 있어도 원격과 같아진다.
로컬에서 고친 것은 없어야 정상이므로 지워도 된다. 이력은 전부 받는다(`--depth` 없음). 문서별 날짜를
`git log` 로 읽어야 하고, 코드를 볼 때도 이력이 필요하기 때문이다. 다른 브랜치와 태그는 받지 않는다.

**토큰은 환경변수로만 git 에 넘긴다.** `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` 로
`http.extraHeader` 에 Basic 인증을 넣는다. clone 주소에 토큰을 넣으면 `.git/config` 에 남는다.
`-c` 인자로 넘기면 프로세스 목록에 보인다. 이 방식은 둘 다 피한다.

**코드 도구는 셋이고, 좁게 만들었다.** 출력이 커져 토큰을 다 쓰거나 리포를 끝없이 뒤지는 일을 막는다.
- `search_code(repo, pattern, path)` — `git grep -E`, 앞뒤 2줄, 최대 200줄.
- `read_code(repo, path, start, end)` — `git show HEAD:<경로>`, 한 번에 최대 300줄. 2MB 를 넘는 파일과 바이너리는 읽지 않는다.
- `code_history(repo, path, commit)` — commit 을 비우면 `git log` 로 최근 커밋 30개(해시·날짜·작성자 이름·제목), 주면 `git show` 로 그 커밋의 메시지와 diff 최대 300줄. 작성자 이메일은 형식에서 빼 주지 않는다. commit 은 16진수 해시만 받아 옵션 주입을 막는다.
- 모두 리포 하나를 지정해야 하고, 기록(`heads`)에 있는 리포만 받는다.

ripgrep 대신 git 을 쓴 이유는, clone 에 어차피 git 이 필요하고 git 이 추적하는 파일만 보기 때문이다.
`.git` 안이나 빌드 산출물은 찾지 않는다. 파일을 경로가 아니라 `HEAD:<경로>` 로 읽으므로
`../` 나 심링크로 리포 밖을 읽을 수 없다.

**코드 도구는 예외로만 쓰게 못박았다.** 벡터 DB 를 쓰는 이유는 짧은 조각 몇 개로 빨리, 토큰을 적게 써서 답하는 데 있다.
요즘 모델은 도구가 있으면 확인 삼아, 덧붙이려고 코드를 뒤지는 경향이 있다. 그러면 질문 하나가 수십 번의 도구 호출로 늘어진다.
그래서 서버 지침에 기준을 적었다. 항상 `search_docs` 를 먼저 부르고, 문서로 답이 되면 코드 도구를 부르지 않는다.
코드 도구는 사용자가 코드·구현·이력을 직접 물었거나, 문서에 답이 없어 위치나 바뀐 시점을 확인해야만 답할 수 있을 때만 쓴다.
쓸 때도 리포와 경로를 좁혀 몇 번 안에 끝내고, 찾지 못하면 멈춘다. 각 도구 설명의 첫머리에도 같은 조건을 넣었다.
지침은 api 모드에서는 붙지 않는다. 코드 도구가 없는데 코드 얘기를 하면 모델이 헷갈린다.
코드 도구는 모델을 쓰지 않으므로 14절의 임베딩 락과는 상관없다.

볼륨은 RWO 라 검색 서버와 수집 파드가 같은 노드에 떠야 한다. 단일 노드라 문제없다.
수집이 `reset` 하는 짧은 동안에는 코드 도구가 바뀌는 중인 파일을 읽을 수 있다. PoC 에서는 받아들였다.

**PoC 에서 아직 확인하지 않은 것.**
- 사내 코드를 이 서버의 볼륨에 둬도 되는지. 이 안을 기본값으로 바꿀지는 이 답에 달렸다.
- 첫 clone 에 걸리는 시간. `concurrencyPolicy: Forbid` 라 길어져도 다음 실행과 겹치지 않고, 다음 실행을 건너뛴다.
- LFS. 이미지에 git-lfs 가 없어서 LFS 파일은 포인터만 받는다.

권한은 따지지 않는다. 검색 서버를 쓰는 팀원 모두가 대상 리포를 볼 수 있다는 전제다.
