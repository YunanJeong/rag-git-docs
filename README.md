# rag-git-docs

GitLab 그룹이나 GitHub 계정에 흩어진 마크다운을 모아 벡터 DB 에 넣고, 자연어로 관련
내용을 찾는 **RAG 파이프라인**.

RAG(Retrieval-Augmented Generation)는 LLM 에게 질문을 던질 때 관련 문서를 함께 넣어주는
방식이다. 모델이 모르는 사내 문서를 근거로 답하게 만들 수 있다. 이때 "어떤 문서가 관련
있는지" 찾아내는 앞단이 이 프로젝트다.

키워드가 아니라 의미로 찾기 때문에 문서에 없는 표현으로 물어도 걸린다.
예를 들어 `워커 늘리는 법` 으로 검색하면 `노드그룹 desired 조정` 문서가 나온다.

찾은 문서 조각을 그대로 돌려준다. LLM 호출은 하지 않는다.

## 필요한 것

- [uv](https://docs.astral.sh/uv/)
- Docker
- 토큰 — GitLab 이면 그룹 액세스 토큰 (스코프 `read_api` + `read_repository`),
  GitHub 이면 PAT (공개 리포만 볼 거면 스코프는 없어도 된다)
- 디스크 5GB (임베딩 모델 bge-m3 를 최초 실행 시 내려받는다)

## 사용법

```bash
# 0. 설정. .env.example 을 복사해 값을 채운다
cp .env.example .env && set -a && . ./.env && set +a

# 1. 의존성 설치
uv sync

# 2. 수집 (SOURCE → DOCS_DIR)
uv run collect.py

# 3. Qdrant 기동
docker run -d --name rag-qdrant -p 6333:6333 -v qdrant_storage:/qdrant/storage qdrant/qdrant

# 4. 색인 (문서를 쪼개 → 숫자로 바꿔 → DB 에 넣는다)
uv run index.py

# 5. 검색
uv run search.py "워커 늘리는 법"
uv run search.py "특정 리전 코드" --top-k 3
```

2 와 4 는 주기가 다르다. 수집만 자주 돌려도 되고, 색인은 문서가 실제로 바뀐 날에만 돌리면 된다.

**토큰을 명령줄에 직접 쓰지 않는다.** 셸 히스토리와 프로세스 목록(`ps`)에 남는다.
`.env` 나 환경변수로 넣는다.

### 수집은 증분, 색인은 전량

`collect.py` 는 파일마다 blob SHA 를 `DOCS_DIR/.manifest.json` 에 기록해 두고
**바뀐 것만 내려받는다.** 아끼는 건 API 트래픽이다.

`index.py` 는 여전히 **매번 컬렉션을 새로 만들고 전부 다시 넣는다.** 문서 1000개 규모면
몇 분이고, 그 대가로 "삭제된 문서의 조각이 DB 에 남는" 문제가 아예 생기지 않는다.

`DOCS_DIR` 에 두는 파일은 **무엇이든 `.md` 로 끝내지 않는다.** `index.py` 가
`rglob("*.md")` 로 긁어가기 때문이다. manifest 가 `.json` 인 이유다.

수집 상태를 완전히 초기화하려면 `DOCS_DIR` 을 통째로 지우면 된다. 다음 실행이 전량 재수집이다.

### 테스트

```bash
uv run pytest -q
```

청킹과 수집 판정 로직만 있다. 모델·Qdrant·네트워크 없이 도니까 `uv sync` 직후 바로 돌아간다.

### 정리

```bash
docker stop rag-qdrant           # 중지 (데이터 유지, docker start 로 재개)
docker rm -f rag-qdrant          # 컨테이너 삭제 (데이터는 볼륨에 남음)
docker volume rm qdrant_storage  # 색인 데이터까지 삭제
rm -rf "$DOCS_DIR"               # 수집한 문서와 manifest 삭제
```

## 환경변수

| 변수 | 기본값 | 용도 |
|---|---|---|
| `SOURCE` | `gitlab` | 어디서 모을지. `gitlab` \| `github` |
| `EXCLUDE_REPOS` | (없음) | 제외할 리포. 쉼표로 구분 |
| `DOCS_DIR` | (필수) | **수집 대상이자 색인 대상.** collect 가 쓰고 index 가 읽는다 |
| `QDRANT_URL` | `http://localhost:6333` | 원격 Qdrant 를 쓸 때 이 값만 바꾼다 |
| `QDRANT_COLLECTION` | `docs` | |
| `EMBED_MODEL` | `BAAI/bge-m3` | 색인과 검색이 같아야 한다 |
| `TOP_K` | `5` | 검색 결과 개수 |

고른 소스의 변수만 있으면 된다. 나머지는 읽지 않는다.

| `SOURCE=gitlab` | 기본값 | |
|---|---|---|
| `GITLAB_GROUP` | (필수) | 대상 그룹. 하위 그룹까지 포함된다 |
| `GITLAB_TOKEN` | (필수) | 그룹 액세스 토큰 |
| `GITLAB_URL` | `https://gitlab.com` | 자체 호스팅이면 바꾼다 |

| `SOURCE=github` | 기본값 | |
|---|---|---|
| `GITHUB_OWNER` | (필수) | 대상 계정 또는 조직 |
| `GITHUB_TOKEN` | (필수) | PAT. 공개 리포만 볼 거면 스코프는 없어도 된다 |
| `GITHUB_API` | `https://api.github.com` | Enterprise Server 면 `https://<호스트>/api/v3` |

GitLab 그룹 액세스 토큰은 **GitLab 16.0 부터 만료일이 필수**이고 최대 365일이다
(gitlab.com 은 무기한 발급이 불가능하다). 배치로 돌린다면 갱신 일정을 잡아둬야 한다.

GitHub 은 공개 리포만 읽더라도 **토큰이 필요하다.** 인증 없이는 시간당 60회라
리포 몇 개에서 막힌다.

## 구조

```
소스 → 수집 → md 파일 → 청킹 → 임베딩 → Qdrant 저장 → 질의 임베딩 → 검색 → 관련 조각
      (바뀐 것만) (쪼개기) (숫자로 바꾸기)         (질문도 숫자로) (가까운 숫자 찾기)
```

모듈 셋이 있고 **서로를 import 하지 않는다.** 조립은 진입점에서만 한다.

```
collect.py  →  sources, collector
index.py    →  rag
search.py   →  rag

sources  ↔  collector  ↔  rag        서로 모른다
```

| 모듈 | 하는 일 | 아는 것 |
|---|---|---|
| `sources/` | 어디서 md 를 받아올지 | GitLab·GitHub API. **벤더 이름이 나오는 유일한 곳** |
| `collector/` | 받을 것·지울 것을 정하고 디스크에 반영 | 경로와 SHA 뿐. 어느 소스에서 왔는지 모른다 |
| `rag/` | md → 조각 → 벡터 → 검색 | 문서 파일과 Qdrant 뿐. 수집을 모른다 |
| `infra/` | EC2 인스턴스 IaC | (별도 테라폼 모듈을 여기에 둔다) |

| 파일 | 하는 일 |
|---|---|
| `sources/types.py` | `Repo` / `Entry` 와 md 선별. git 객체 모델이라 벤더 공용이다 |
| `sources/_http.py` | GET, 재시도, `Link` 헤더 페이지네이션. 헤더 dict 를 받을 뿐 벤더를 모른다 |
| `sources/gitlab.py` | GitLab URL 모양과 필드 이름. 자기 환경변수는 자기가 읽는다 |
| `sources/github.py` | GitHub 쪽 같은 것. 트리가 `truncated` 로 오는지 본다 |
| `collector/manifest.py` | 받을 것·지울 것 판정. **가져다 쓰는 모듈이 하나도 없다** |
| `collector/files.py` | md 쓰기·지우기, manifest 읽기·쓰기 |
| `rag/chunk.py` | md 를 헤더 단위로 자른다. 조각 앞에 `[파일 > 헤딩]` 한 줄을 붙여 맥락을 남긴다 |
| `rag/embed.py` | bge-m3 로 텍스트를 벡터로 바꾼다 |
| `rag/store.py` | Qdrant 컬렉션 생성 / 저장 / 검색 |
| `collect.py` | 소스의 md 를 `DOCS_DIR` 로 모은다. `SOURCE` 와 `DOCS_DIR` 만 안다 |
| `index.py` | `DOCS_DIR` 아래 md 를 전부 읽어 색인한다 |
| `search.py` | 질의하고 결과를 출력한다 |

**소스를 하나 더 붙이려면** `sources/` 에 파일 하나를 추가하고
`sources/__init__.py` 의 dict 에 한 줄 넣으면 된다. 진입점은 고치지 않는다 —
벤더 환경변수를 각 소스 모듈이 자기가 읽기 때문이다.

## 만들어가는 과정

각 단계가 앞 단계에서 막힌 것을 푸는 순서로 되어 있다. 위에서부터 읽으면 된다.

### 출발점 — 애초에 왜 필요한가

사내 문서를 근거로 LLM 에게 묻고 싶다. 문서가 몇 개뿐이면 **그냥 프롬프트에 파일을
붙여넣으면 된다.** 이 프로젝트는 필요 없다.

문제는 문서가 늘어날 때다. 다 넣으면 컨텍스트에 안 들어가고, 넣을 수 있어도 대부분이
질문과 무관한 내용이라 답이 나빠진다. 그래서 **질문과 관련 있는 부분만 골라내는 앞단**이
필요해진다. 이 프로젝트가 그 앞단이다.

그리고 그 문서들은 한 폴더에 얌전히 있지 않다. 리포 수십 개에 각각 `docs/` 나
`README.md` 로 흩어져 있다. **모으는 것부터가 일이다.**

### 1. 모으기 — `git clone` 을 쓰지 않는 이유

리포를 전부 clone 하면 수집 서버에 **원본 저장소의 사본이 생긴다.** 필요한 건 md 본문뿐인데
`.git` 에는 전체 파일 목록, 커밋 메시지, 작성자 이메일, 과거 이력이 전부 따라온다.
문서 검색 서버가 사고 나면 유출되는 범위가 달라진다.

→ **REST API 로 md 만 받는다.** 리포 목록 → 파일 트리 → blob 내용, 세 번의 호출이다.

채택하지 않은 대안: `--depth 1 --filter=blob:none`, sparse-checkout. 용량은 줄지만
`.git` 이 남는다는 점은 같다.

파일을 받을 때 **경로가 아니라 blob SHA 로 요청한다.** `files/:path/raw` 는 경로를
URL 인코딩해야 하는데, 한글·공백·`#` 이 든 경로에서 인코딩이 한 번 어긋나면 404 다.
SHA 는 16진수라 그 문제가 없다.

### 2. 매번 전부 받으면 안 되나 — manifest 와 blob SHA

리포 수십 개를 매번 전부 내려받으면 API 에 부담이고 느리다.
그런데 API 로 받으면 `git pull` 이 공짜로 해주던 "뭐가 바뀌었나"를 알 수 없다.

→ 파일 트리에 **blob SHA 가 같이 온다.** 경로 → SHA 를 `.manifest.json` 에 적어두고,
SHA 가 같으면 내려받기를 건너뛴다.

SHA 는 **내용의 해시**다. 그래서 브랜치를 `master` → `main` 으로 바꿔도, 파일을
옮겼다가 되돌려도, 내용이 같으면 재다운로드가 일어나지 않는다. 수정 시각 기반이었다면
이 중 어느 것도 성립하지 않는다.

### 3. GitLab 과 GitHub 은 얼마나 다른가

같은 코드로 둘 다 된다고 말하기는 쉽다. 실제로 짜 보면 **공용인 부분과 아닌 부분이
분명하게 갈린다.**

| | 공용 | 벤더별 |
|---|---|---|
| HTTP GET, 재시도, `Link` 헤더 파싱 | ✓ | |
| md 선별 (`type=="blob"`, mode ≠ 심링크·서브모듈, `.md`) | ✓ | |
| manifest 대조, 삭제 판정, 파일 쓰기 | ✓ | |
| 청킹, 임베딩, 저장 | ✓ | |
| 인증 헤더 이름 | | `PRIVATE-TOKEN` vs `Authorization: Bearer` |
| 엔드포인트 URL 세 개 | | 모양이 다르다 |
| 리포 경로 필드 | | `path_with_namespace` vs `full_name` |
| 트리 SHA 필드 | | `id` vs `sha` |

**md 선별이 공용인 게 핵심이다.** `type: "blob"` 과 mode 값 `100644`·`120000`·`160000` 은
git 객체 모델을 그대로 내보낸 것이라 두 벤더가 글자까지 같다. 껍데기만 다르지 같은 git 이다.

그래서 호출 흐름(리포 목록 → 트리 → blob)은 동일하고, **벤더 파일은 각 30줄쯤**이다.
ABC 도 Protocol 도 팩토리도 두지 않았다 — 구현체가 둘뿐이라 dict 조회 한 줄이면 된다.

**진짜로 동작이 다른 건 하나다.** GitHub 의 트리 API 는 페이지네이션이 없다.
`?recursive=1` 로 전부 주거나, 너무 크면 `"truncated": true` 를 붙여 **앞부분만 준다.**
이걸 안 보면 "파일이 사라졌다"로 읽혀 4절의 삭제 로직이 멀쩡한 문서를 지운다.
그래서 `github.py` 는 `truncated` 를 보고 예외를 던지고, 그 리포는 삭제 대상에서 빠진다.

### 4. 경로를 평평하게 펴면 안 되나

`repo-a/docs/deploy.md` 와 `repo-b/docs/deploy.md` 를 한 폴더에 넣으면 이름이 부딪힌다.
해시를 붙여 `deploy-a3f1.md` 로 만들면 충돌은 없어진다.

→ **원본의 디렉터리 구조를 그대로 유지한다.** `DOCS_DIR/<리포 경로>/docs/deploy.md`.

이유는 6절에 있다. 청킹이 파일 경로를 조각의 맥락(브레드크럼)으로 쓰기 때문에,
경로를 뭉개면 검색 품질이 같이 뭉개진다. 저장 구조가 검색 품질에 직접 연결된다.

### 5. 삭제가 제일 무섭다

문서가 지워지면 로컬에서도 지워야 한다. 안 그러면 없어진 문서가 검색에 계속 나온다.
그런데 삭제 로직은 잘못 돌면 **문서를 날린다.** 세 겹으로 막았다.

**첫째, 조회에 성공한 리포만 삭제 대상이다.** 트리 API 가 500 이나 403 을 던졌을 때
"파일이 하나도 없다"로 읽으면 그 리포 문서가 통째로 지워진다. 일시적인 네트워크 장애로
문서가 날아가는 셈이다. 실패한 리포는 삭제 계산에서 아예 빠진다.

**둘째, manifest 에 기록된 파일만 지운다.** `rmtree` 로 디렉터리를 통째로 날리지 않는다.
`DOCS_DIR` 을 잘못 잡아 홈 디렉터리를 가리켰을 때, 수집기가 적어둔 적 없는 파일은
건드릴 수 없다는 보장이 여기서 나온다.

**셋째, 삭제에 실패하면 manifest 에서 그 항목을 지우지 않는다.** 실패했는데 기록을
지우면 다음 실행에서 다시 시도하지 못하고 그 파일이 영구히 남는다.

### 6. 청킹(쪼개기) — 그런데 맥락이 날아간다

관련된 부분만 넘기려면 처음부터 조각 단위로 저장해야 한다. 문서를 이렇게 조각내는 걸
**청킹(chunking)** 이라고 한다. 여기서는 헤더를 기준으로 자른다.

그랬더니 새 문제가 생겼다. 조각만 떼어 놓으니 무슨 얘긴지 모르겠다. `재발급하면 통계가
끊긴다` 라는 조각은 어느 리전 문서인지, 무엇을 재발급한다는 건지 알 수 없다.

→ 조각 앞에 `[파일 > 헤딩]` 한 줄을 붙여 같이 저장한다. 맥락도 검색 대상에 포함된다.
4절에서 경로 구조를 유지한 이유가 이것이다.

같은 이유로 **수집할 때 BOM 을 떼어낸다.** BOM 이 남으면 첫 줄이 `﻿# 제목` 이 되어
헤딩 정규식에 안 걸리고, 문서 전체가 헤딩 없는 한 덩어리가 되면서 브레드크럼을 잃는다.
수집기의 한 줄이 검색 품질을 좌우하는 지점이다.

### 7. 임베딩(숫자로 바꾸기) — 문자열 비교로는 관련 문서를 못 찾는다

`쿠버네티스 워커 늘리기` 와 `노드그룹 desired 조정` 은 **겹치는 글자가 하나도 없는데
같은 얘기일 수 있다.** Elasticsearch 처럼 글자로 색인하는 저장소는 유의어 사전을 사람이
직접 채우지 않는 한 못 찾는다.

→ 조각을 **숫자 목록(vector)** 으로 바꿔서 저장한다. 이 변환이 **임베딩(embedding)**,
변환해주는 AI 모델이 **임베딩 모델**이다.

```
"노드그룹 desired 조정"   →  [0.21, -0.04, 0.88, ... ]   ← 숫자 1024개
"쿠버네티스 워커 늘리기"  →  [0.19, -0.07, 0.85, ... ]   ← 값이 비슷하다
"배포 스크립트 롤백"      →  [-0.63, 0.41, 0.02, ... ]   ← 값이 다르다
```

뜻이 비슷하면 숫자도 가까워지도록 학습된 모델이다. 그래서 "의미가 비슷한가"를 **숫자 사이의 거리 계산**으로 바꿀 수 있고, 그 계산을 대신해주는 저장소가 **벡터 DB** 다.

단, **DB 는 의미를 모른다.** 의미를 아는 건 임베딩 모델뿐이다. 그래서 넣을 때 한 번 돌리고
끝이 아니라 **검색할 때마다 질문도 같은 모델로 벡터로 바꿔** 넘겨야 하고, DB 는 받은 벡터로
가까운 것만 찾아준다. 색인과 다른 모델을 쓰면 값이 안 맞아 결과가 무의미해진다 —
`EMBED_MODEL` 이 색인·검색 공통 설정인 이유다.

> 임베딩 모델은 **LLM(언어생성모델) 이 아니다.** 글을 쓰는 게 아니라 벡터로 바꾸는 것만 학습한 별개 모델군이다. Claude Code 를 이 DB 에 붙이면 답은 Anthropic 모델(Claude Opus 등)이, 벡터는 bge-m3 가 만든다. Anthropic 은 임베딩 API 가 없어 그 자리는 항상 별도 모델이다.

### 8. 어떤 임베딩 모델을 쓰나 — 문서를 밖으로 내보낼 순 없다

OpenAI 임베딩 API 같은 걸 쓰면 색인할 때마다 사내 문서 전문이 외부로 나간다.
1절에서 clone 을 피한 이유와 같은 종류의 문제다.

→ **bge-m3** 를 로컬에서 돌린다. 문서가 나가지 않고 API 키도 필요 없다. 다국어 모델이라 한국어가 되고, 8번에 필요한 두 종류 벡터를 한 번에 내준다.

### 9. 의미로만 찾으면 고유명사를 구별 못 한다

사내 리전 코드처럼 **한 글자만 다른 식별자**로 검색하면 엉뚱한 문서가 같이 딸려 나온다.
임베딩 모델이 학습한 적 없는 사내 고유명사라서, 둘이 거의 같은 숫자가 되기 때문이다.

→ 성격이 반대인 **두 종류의 벡터**를 같이 쓴다. bge-m3 가 둘 다 내준다.

- **dense**(밀집) — 지금까지 말한 그 1024개 숫자. 문장 전체의 뜻을 담는다.
- **sparse**(희소) — 단어 하나가 칸 하나인 아주 긴 목록. 그 조각에 나온 단어의 칸에만
  중요도 점수가 들어가고 나머지는 전부 0 이라 "희소"다. 같은 단어가 글자 그대로
  나와야 점수가 붙는다.

```
sparse:  ... region-a: 0.8 ... serverid: 0.6 ... (나머지 수만 칸은 0)
```

| | 잘하는 것 | 못하는 것 |
|---|---|---|
| **dense** | 표현이 달라도 뜻이 같으면 찾음 | 한 글자 다른 식별자 구별 |
| **sparse** | 글자가 정확히 맞는 것을 찾음 | 표현이 다르면 못 찾음 |

두 검색을 각각 돌리고 순위를 합친다(RRF). 한쪽의 약점을 다른 쪽이 메운다.

### 10. 어떤 벡터 DB 를 쓰나 — Chroma vs Qdrant

| | Chroma | Qdrant |
|---|---|---|
| 형태 | 파이썬 라이브러리. 임포트하면 끝 | 서버. 컨테이너로 띄운다 |
| 쓰는 자리 | 노트북, 프로토타입 | 여러 클라이언트가 붙는 공용 검색 |

Chroma 가 훨씬 간편하지만 쓰지 않았다. **Chroma 로 충분한 규모면 출발점으로 돌아가
프롬프트에 파일을 붙여넣는 게 낫기 때문이다.** 벡터 DB 가 값을 하는 건 문서가 많아
다 못 넣거나 여러 사람이 색인을 공유할 때고, 그 지점을 목표로 하면 처음부터 서버형이
맞다.

### 11. 수집은 증분인데 색인은 전량이다

여기까지 왔으면 자연스러운 다음 수순이 있다. `collect.py` 가 어느 파일이 바뀌었는지
이미 알고 있으니, 그걸 `index.py` 에 넘겨 바뀐 문서만 다시 색인하면 된다.

**하지 않았다.** `store.py` 는 매번 컬렉션을 통째로 다시 만든다. 그 덕에 "삭제된 문서의
조각이 DB 에 남는" 문제가 아예 생기지 않는다 — 5절에서 파일 삭제를 세 겹으로 막아야 했던
그 종류의 문제를, 색인 쪽에서는 공짜로 피하고 있는 셈이다.

증분 색인으로 바꾸면 그 방어를 벡터 DB 쪽에도 다시 짜야 한다. 문서 1000개 규모에서
전량 재색인이 몇 분이면 끝나니, **실제로 안 견딜 때 한다.**

### 12. 왜 폴더를 셋으로 나눴나

처음엔 전부 `rag/` 에 넣고 `rag/gitlab.py`, `rag/sync.py` 로 두었다. 돌아는 갔다.
문제는 **레포 이름이 `rag-git-docs` 인데 `gitlab` 이 여기저기 박혀 있었다는 것**이다.
GitHub 을 붙이려면 여러 파일을 동시에 고쳐야 하는 상태였다.

경계를 어디에 그을지는 폴더 깊이가 아니라 **무엇을 아느냐**로 정했다.

| 모듈 | 아는 것 | 모르는 것 |
|---|---|---|
| `sources/` | API 주소, 인증 헤더, 필드 이름 | 파일을 어디에 쓰는지, 벡터가 뭔지 |
| `collector/` | 경로와 SHA | 그게 어느 벤더에서 왔는지 |
| `rag/` | md 파일과 Qdrant | 그 파일이 어떻게 생겼는지 |

세 모듈은 **서로를 import 하지 않는다.** 조립은 진입점 세 개에서만 일어난다.

검증 방법이 하나 있다. `collector/manifest.py` — 문서가 날아가는 가장 위험한 코드 —
는 **가져다 쓰는 모듈이 하나도 없다.** `dict[str, str]` 두 개를 받아 리스트를 돌려줄
뿐이다. 그래서 네트워크도 디스크도 없이 전부 테스트로 묶인다. 경계가 제대로 그어졌다는
증거를 "의존성이 없다"로 확인할 수 있는 셈이다.

`Entry` 객체를 받게 했다면 이게 안 됐다. **시그니처를 좁히는 것이 추상화 계층을 만드는
것보다 경계를 더 잘 긋는다** — ABC 를 두면 의존성이 생기지만, `dict` 를 받으면 사라진다.

`rag/` 는 별도 PoC 에서 통째로 복사해 온 모듈이고, `infra/` 는 EC2 테라폼 모듈이
들어올 자리다. **둘 다 이 레포에서 태어나지 않았다.** 그게 가능한 이유도 같다 —
서로를 모르기 때문이다.
